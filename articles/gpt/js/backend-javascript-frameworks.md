# Серверные JavaScript-фреймворки: разбор и выбор для проекта

В JavaScript-разработке на бэкенде нет одного фреймворка, который одновременно задаёт такую же общую структуру проекта и набор встроенных компонентов, как Rails или Symfony. Под словом «фреймворк» здесь могут иметь в виду и HTTP-роутер, и платформу приложения с ORM, и инструмент для сборки full-stack проекта.

Ещё одно важное различие: **Node.js — это runtime для JavaScript**, а Express, NestJS и другие — фреймворки, работающие поверх runtime. Многие из них пишут на TypeScript и запускают скомпилированный JavaScript. [Что такое Node.js](https://nodejs.org/en/about/).

Это открытый добровольный опрос: полезный срез сообщества, но не точная доля всех production-систем. [Результаты State of JS 2025](https://2025.stateofjs.com/en-US/libraries/back-end-frameworks/), [методика и описание опроса](https://2025.stateofjs.com/en-US/about/).
- Звёзды GitHub показывают накопленный интерес к репозиторию.
- Загрузки основного npm-пакета за последнюю полную неделю — **28 сентября — 4 октября 2026 года** — дают текущий сигнал использования пакетов.

Звёзды и загрузки в таблице кликабельны. Число npm-загрузок не равно числу разработчиков или работающих приложений: это запросы на скачивание пакета, включая CI и транзитивные зависимости. Этот список шире и включает frontend- и backend-технологии вместе, поэтому State of JS даёт более предметный срез именно по серверным фреймворкам. ## Что именно сравнивается

- **HTTP-фреймворк** принимает запрос, выбирает маршрут и формирует ответ. В Express, Fastify и Hono команда обычно сама добавляет ORM, авторизацию и фоновые задачи.
- **Application-фреймворк** предлагает структуру проекта и общие правила. В Nest это модули и DI; в AdonisJS — MVC, ORM, миграции и другие связанные компоненты.
- **Middleware и hooks** — точки, где можно обработать запрос до или после основной логики: например, проверить авторизацию, записать журнал или проверить входные данные.
- **ORM** связывает код приложения с базой данных, а миграции описывают изменения схемы. Они входят в некоторые фреймворки и подключаются отдельно в других.

Поэтому звёзды и недельные загрузки сами по себе не отвечают на вопрос, что быстрее доведёт конкретный проект до production: сравнивайте и объём готовых частей, и runtime, и выбранную базу.

## Общая основа Node.js

Express, NestJS, Fastify и Koa используют Node.js; замена одного на другой сама по себе не устраняет блокирующий CPU-код. Асинхронный ввод-вывод Node умеет обрабатывать без ожидания каждого запроса. Долгие синхронные вычисления в обработчике занимают event loop и мешают обслуживать остальные запросы. Для CPU-intensive задач Node.js предлагает Worker Threads; создавайте пул рабочих потоков, а не новый поток на каждый короткий запрос. [Руководство Node.js по event loop и worker pool](https://nodejs.org/learn/asynchronous-work/dont-block-the-event-loop), [Worker Threads](https://nodejs.org/api/worker_threads.html).

## Что ближе всего к Rails и Symfony

### Если хочется «батарейки» и MVC

Сначала смотрите на **AdonisJS**. Его компоненты задуманы как согласованный набор для полноценного приложения: маршруты, модели, миграции, валидация и авторизация. Это наиболее прямой вариант, если Rails/Symfony нравится именно как среда для создания бизнес-приложения, а не только как роутер.

**Sails.js** также использует MVC и поставляет ORM. Перед выбором проверьте драйверы Waterline для вашей базы, актуальность нужных плагинов и насколько команде подходит его экосистема.

### Если важнее структура и зависимостей много

**NestJS** даёт архитектуру модулей и DI, которая помогает разделять большие приложения по доменам и подключать компоненты. В стандартном HTTP-приложении он использует Express adapter; можно выбрать Fastify. Базы, ORM и многие инфраструктурные возможности подключаются отдельными модулями.

Поэтому NestJS структурно похож на enterprise-фреймворки с контейнером зависимостей, а AdonisJS ближе к цельному MVC-набору с меньшим количеством самостоятельных решений.

### Если нужен быстрый HTTP API

- **Fastify** — когда нужны схемы запросов/ответов, плагины и аккуратный HTTP-слой.
- **Express** — когда важны совместимость, простота и имеющийся middleware ecosystem.
- **Hono** — когда один набор маршрутов должен работать в Node.js, Bun, Deno или edge runtime.
- **Koa** — когда нужна минимальная основа и у команды есть собственные правила организации сервера.

Эти варианты не выбирают по одной цифре benchmark. Сначала задайте реальные требования к валидации, работе с базой, авторизации, логированию и deployment.

## Как выбрать для конкретной задачи

| Задача | С чего начать |
|---|---|
| Бизнес-приложение с базой, миграциями, авторизацией и обычными CRUD-экранами | **AdonisJS**; **Sails.js** — если подходит MVC и Waterline |
| Большой API и несколько команд на TypeScript | **NestJS** |
| API с чёткими JSON-контрактами и тонким HTTP-слоем | **Fastify** |
| Существующий Express-код, много middleware или нужно легко нанимать людей под знакомый стек | **Express** |
| Одни маршруты для Node, serverless и edge | **Hono** |
| Проект на Bun с type-safe API | **Elysia** |
| Realtime-сервисы через REST и WebSocket | **Feathers**; **Meteor** — если нужен весь full-stack подход |
| Соединить API с разными базами и внешними сервисами | **LoopBack 4** |
| Несколько внутренних сервисов с межсервисными вызовами и транспортами | **Moleculer** |
| API и админка вокруг контента | **Strapi** |
| API и data studio поверх существующей SQL-базы | **Directus** |
| UI на Next/Nuxt и серверные маршруты для его API | Server routes выбранного full-stack-фреймворка; отдельный backend можно выделить при росте доменной логики |

Мой короткий список, если проект новый:

1. **AdonisJS** — когда нужен самый цельный MVC-путь, похожий на Rails.
2. **NestJS** — когда нужна строгая структура TypeScript-приложения и много модулей.
3. **Fastify** — когда хочется собирать backend из небольших частей, но иметь удобную валидацию и плагины.
4. **Express** — когда ценны простой порог входа, широкая совместимость и существующий код.
5. **Hono** — для переносимых и edge/serverless API.

## Проверки перед внедрением

Не выбирайте фреймворк только по внешнему сходству с Rails или по количеству звёзд. Проверьте по небольшому vertical slice реального приложения:

- как устроены транзакции, миграции, связи и пул соединений с вашей базой;
- есть ли поддерживаемые библиотеки для авторизации, сессий, фоновых задач и планировщика;
- как валидируются входные данные и сериализуются ответы;
- можно ли сгенерировать OpenAPI/SDK или использовать типобезопасный контракт;
- как устроены тестирование, логирование, request ID, метрики и трассировка;
- работает ли нужная версия Node.js LTS либо выбранный Bun/edge runtime;
- насколько часто выходят исправления, совместимы ли плагины с текущей major-версией;
- сколько кода нужно написать, чтобы реализовать одну операцию от HTTP-запроса до базы и теста.

В компании важна и уже накопленная экспертиза команды: миграция на новый фреймворк имеет смысл, если даёт конкретное преимущество для проекта, а не только более модную структуру.
