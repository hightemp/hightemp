# Как закрепить IP Packagist для Packeton в Docker Compose

Иногда Packeton не может обратиться к Packagist по доменному имени: выбранный DNS-адрес недоступен из сети контейнера или маршрут до него работает с перебоями. В таком случае можно временно направить `repo.packagist.org` на заранее проверенный IP, оставив в Packeton исходный HTTPS URL.

Здесь важно различать **закрепление адреса** и **резервирование**. `extra_hosts` закрепляет соответствие имени одному адресу внутри контейнера. Если этот адрес перестанет отвечать, Docker Compose сам не переключится на DNS или другой IP.

## Что настраивается в Packeton

В документации Packeton зеркало описывается так:

```yaml
packeton:
  mirrors:
    packagist:
      url: https://repo.packagist.org
      sync_lazy: true
      enable_dist_mirror: true
```

Документированный пример задаёт для зеркала один `url`. Отдельный параметр `fallback_url` или список upstream-адресов в этой конфигурации не описан. Опции `sync_lazy` и `enable_dist_mirror` относятся к синхронизации зеркала и выдаче дистрибутивов; выбор IP для сетевого соединения они не меняют. См. [документацию Packeton о зеркалах](https://docs.packeton.org/usage/mirroring.html).

Оставьте URL доменным: `https://repo.packagist.org`. Тогда клиент подключается по IP, заданному для домена на уровне контейнера, но TLS-проверка по-прежнему выполняется для имени `repo.packagist.org`. Не заменяйте URL на `https://<IP>`: сертификат HTTPS обычно выпущен на доменное имя, а не на IP.

## Добавьте mapping в Compose

В существующее описание сервиса Packeton добавьте `extra_hosts`:

```yaml
services:
  packeton:
    extra_hosts:
      - "repo.packagist.org=${PACKAGIST_IP:?Set PACKAGIST_IP in .env}"
```

Если у `packeton` уже есть `extra_hosts`, добавьте строку в существующий список, сохранив прежние записи. Короткий формат `HOST=IP` поддерживается Compose. Для Linux Docker добавляет соответствие имени и IP в `/etc/hosts` контейнера. [Справочник Docker Compose: `extra_hosts`](https://docs.docker.com/reference/compose-file/services/#extra_hosts).

В `.env`, который Compose использует для подстановки, задайте проверенный IPv4-адрес:

```dotenv
PACKAGIST_IP=192.0.2.10
```

`192.0.2.10` — учебный адрес из блока, зарезервированного для документации RFC 5737; он не предназначен для реального подключения. Перед запуском замените его на адрес, который проверили из нужной сети. Если Compose-файл называется иначе или файл переменных лежит отдельно, укажите их параметрами `-f` и `--env-file`.

Форма `${PACKAGIST_IP:?...}` просит Compose завершиться с ошибкой, если переменная отсутствует или пуста. Это помогает не создать контейнер с некорректной строкой в `extra_hosts`. Compose подставляет значение из окружения запуска, `--env-file` или проектного `.env`; переменная в `.env` сама по себе **не становится переменной окружения внутри контейнера**. Здесь она нужна, чтобы заполнить Compose-конфигурацию. [Интерполяция переменных в Docker Compose](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/).

Проверьте результат подстановки:

```bash
docker compose config
```

В итоговой конфигурации у сервиса `packeton` должна появиться запись с реальным IP. Не публикуйте полный вывод команды, если в Compose-конфигурации есть секреты.

## Как выбрать и проверить адрес

Не берите IP из случайного примера и не считайте однажды полученный DNS-ответ постоянным адресом Packagist. Убедитесь, что выбранный IP доступен **из той же сети**, где работает Packeton, принимает HTTPS на порту 443 и отдаёт корректный сертификат для `repo.packagist.org`.

Если на машине, с которой Packeton сможет выйти в сеть, установлены `curl` и DNS-утилиты, сначала посмотрите текущие ответы:

```bash
getent ahostsv4 repo.packagist.org
```

Затем проверьте каждый предполагаемый адрес, сохраняя доменное имя в URL и сертификатной проверке:

```bash
PACKAGIST_IP=203.0.113.10

curl --fail --silent --show-error \
  --resolve "repo.packagist.org:443:${PACKAGIST_IP}" \
  --output /dev/null \
  --write-out 'HTTP %{http_code}\n' \
  https://repo.packagist.org/packages.json
```

Здесь `203.0.113.10` тоже только пример из документационного диапазона — подставьте проверяемый адрес. `curl --resolve` направляет именно этот запрос на указанный IP, но оставляет URL доменным. Успешный ответ подтверждает доступность HTTPS-ресурса из места запуска `curl`; он ещё не доказывает, что маршрут из Docker-контейнера такой же.

После применения Compose проверьте разрешение имени внутри самого Packeton:

```bash
docker compose exec packeton getent ahostsv4 repo.packagist.org
docker compose exec packeton curl --fail --silent --show-error \
  --output /dev/null --write-out 'HTTP %{http_code}\n' \
  https://repo.packagist.org/packages.json
```

Первая команда должна показать настроенный IP, вторая — успешный HTTPS-ответ. В минимальном образе может не быть `getent` или `curl`; не устанавливайте диагностические пакеты в работающий production-контейнер только ради проверки. Используйте временный диагностический контейнер в той же Docker-сети. Если `curl` сообщает об ошибке сертификата, не отключайте проверку TLS: перепроверьте адрес и сертификат на выбранном endpoint.

## Где ещё нужна запись

`extra_hosts` задаётся на уровне Compose-сервиса. Запись для `packeton` действует только в контейнерах этого сервиса; она не меняет `/etc/hosts` хоста и не распространяется автоматически на соседние контейнеры.

Добавьте такое же соответствие каждому отдельному сервису, который сам обращается к Packagist: например, выделенному worker, cron-задаче или одноразовому CLI-сервису. Не добавляйте его всем контейнерам без необходимости.

Если `composer install` или другой запрос к Packagist выполняется во время `docker build` в инструкции `RUN`, настройки работающего контейнера не влияют на этот этап. Для сборки у Compose есть отдельное поле `build.extra_hosts`; проверьте его по [спецификации сборки Compose](https://docs.docker.com/reference/compose-file/build/#extra_hosts) и настройте только если запрос действительно выполняется при сборке образа.

## Обновление конфигурации

После изменения `.env` проверьте разрешённую конфигурацию и пересоздайте затронутый сервис:

```bash
docker compose config
docker compose up -d packeton
```

При изменении конфигурации `docker compose up` пересоздаёт контейнеры сервиса с новой настройкой. Обычный `docker compose restart packeton` перезапускает старый контейнер и не применяет изменённую конфигурацию. Если используются отдельные worker или cron-сервисы, пересоздайте и их. [Документация `docker compose up`](https://docs.docker.com/reference/cli/docker/compose/up/).

В production сначала проверьте разрешённую конфигурацию, выбранный файл Compose и планируемые к пересозданию сервисы. Эта статья описывает настройку; она не выполняет никаких команд на сервере.

## Почему это не автоматический failover

С `extra_hosts` контейнер получает локальную запись примерно такого вида:

```text
192.0.2.10 repo.packagist.org
```

При запросе `https://repo.packagist.org` имя сопоставляется с заданным адресом. Если IP устарел, сервер недоступен или соединение блокирует сеть, запрос завершится ошибкой. Compose не проверяет доступность адреса и не подставляет следующий IP из DNS. Обновить mapping можно изменением `.env` и пересозданием соответствующих контейнеров.

Поэтому `extra_hosts` подходит для точечной диагностики или управляемого временного закрепления адреса, когда есть известный рабочий IP и понятный процесс его перепроверки. Если требуется автоматическое переключение при отказе, используйте сетевое решение, которое умеет проверять upstream и переключать трафик, например контролируемый HTTP(S)-proxy или балансировщик. Одной статической строки в Compose для отказоустойчивости недостаточно.

## Чек-лист

- [ ] Уточнить, какой процесс действительно запрашивает `repo.packagist.org`: Packeton, worker, cron, CLI или сборка образа.
- [ ] Проверить выбранный IP из той же сети, включая TCP/443, HTTPS-ответ и TLS-сертификат домена.
- [ ] Оставить в Packeton URL `https://repo.packagist.org`.
- [ ] Добавить mapping только сервисам, которые сами выполняют запрос.
- [ ] Убедиться через `docker compose config`, что Compose подставил нужный IP.
- [ ] Пересоздать затронутые контейнеры и проверить имя и HTTPS уже из контейнерной сети.
- [ ] Записать, кто и когда повторно проверяет IP; помнить, что это закрепление адреса, а не автоматический резерв.
