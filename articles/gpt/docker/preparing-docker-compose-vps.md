# Подготовка Docker Compose на VPS: безопасный запуск сайта

Docker Compose упрощает сборку и запуск приложения, но сам по себе не делает сайт безопасным. На VPS нужно отдельно защитить операционную систему, Docker Engine, контейнеры, сеть, данные и процесс обновления.

Ниже — базовая схема для одного Linux VPS с одним публичным сайтом: reverse proxy принимает HTTP/HTTPS, приложение и база данных работают в отдельных контейнерах, данные хранятся вне файловой системы контейнера. Для хостинга недоверенных клиентов на одном сервере контейнеров может быть недостаточно: они используют общее ядро Linux, а не отдельные ядра виртуальных машин. [Docker описывает это в модели безопасности Engine](https://docs.docker.com/engine/security/).

## Сначала определите границы доступа

Внешние пользователи должны попадать только в reverse proxy. Приложение доступно ему по внутренней сети Compose, а база данных — только приложению. Администрирование сервера идёт отдельно через SSH или VPN.

```text
Интернет ── 80/443 ──> Nginx / Caddy / Traefik
                              │ сеть web
                              ▼
                         приложение
                              │ сеть data
                              ▼
                         база данных

Администратор ── SSH/VPN ──> VPS и Docker Engine
```

Снаружи не должны быть доступны порты приложения, базы данных, Redis, панели управления или самого Docker API. Не монтируйте `/var/run/docker.sock` в приложение: доступ к сокету даёт возможность управлять Docker от имени хоста и фактически может привести к получению прав root.

## Подготовьте сам VPS

Установите поддерживаемый Linux из чистого образа и сразу примените обновления безопасности. Заведите отдельную административную учётную запись с `sudo`, настройте вход по SSH-ключу и проверьте вход во второй сессии. Отключайте вход root и парольную аутентификацию только после того, как убедились, что ключевой доступ работает.

Настройте правила и в панели провайдера, и на самом сервере. Обычно публично нужны только SSH (лучше ограничить его своим IP или VPN), HTTP и HTTPS. Точные правила зависят от сети и провайдера.

На Linux опубликованные Docker-порты могут обходить правила `ufw`: Docker перенаправляет трафик до цепочек, которыми пользуется `ufw`. Поэтому не полагайтесь только на вывод `ufw status`; ограничьте публикуемые порты и проверьте доступность с внешней машины. Это поведение описано в [документации Docker по firewall](https://docs.docker.com/engine/network/packet-filtering-firewalls/).

Установите Docker Engine и Compose plugin из официального репозитория Docker по инструкции для своего дистрибутива. Например, для Ubuntu добавьте официальный apt-репозиторий и установите пакеты так:

```bash
sudo apt-get update
sudo apt-get install ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF

sudo apt-get update
sudo apt-get install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

Для Debian используйте Debian-инструкцию, а не Ubuntu URL. Не применяйте установочный convenience-скрипт как стандартный способ production-установки: Docker рекомендует его для тестирования и разработки. После установки проверьте версии и запуск демона. Если не настроен rootless-режим, обращайтесь к Docker через `sudo`:

```bash
sudo docker version
sudo docker compose version
sudo systemctl status docker --no-pager
sudo docker run --rm hello-world
```

Сверяйте команды с [официальной инструкцией установки Docker Engine](https://docs.docker.com/engine/install/) для выбранной версии ОС.

Доступ к Docker — административное полномочие. Членство в группе `docker` предоставляет права уровня root, поэтому не добавляйте туда пользователя сайта, обычного разработчика или CI-агента без оценки последствий. В дальнейших командах используется `sudo`; без него к демону подключается только пользователь с соответствующими правами или rootless-установкой. Docker API не нужно публиковать на TCP-порту без TLS. Для удалённого управления используйте SSH-контекст Docker или другой защищённый способ из [документации](https://docs.docker.com/engine/security/protect-access/). Установка Docker в [rootless-режиме](https://docs.docker.com/engine/security/rootless/) может снизить последствия компрометации демона, но требует отдельной проверки сетей, томов, лимитов ресурсов и привилегированных портов.

## Собирайте образ как артефакт релиза

В production приложение должно запускаться из собранного образа. Не монтируйте весь исходный код с VPS внутрь работающего контейнера: при таком подходе поведение сервера зависит от содержимого хоста, а процесс приложения часто получает лишние права на файлы.

Используйте доверенный базовый образ, многоэтапную сборку и `.dockerignore`. Если приложению не нужны root-права, задайте `USER` в Dockerfile. Docker рекомендует это в [руководстве по сборке образов](https://docs.docker.com/build/building/best-practices/).

Не кладите `.env`, приватные ключи, дампы баз и каталоги резервных копий в build context. Добавьте production-конфигурацию с локальными параметрами и каталог секретов в `.gitignore`:

```gitignore
.env.production
/secrets/
```

А в `.dockerignore` исключите их из build context:

```dockerignore
.git
.env
.env.*
!.env.example
secrets/
backups/
```

Не передавайте пароли и токены через Dockerfile `ARG` или `ENV`: они могут остаться в слоях образа или метаданных сборки. Для доступа к приватному репозиторию или пакету используйте временные BuildKit secret mounts, а не сохранение ключа в образе ([документация Docker](https://docs.docker.com/build/building/secrets/)).

Не используйте `latest` как стратегию обновления. Фиксируйте проверенную версию образа, а для воспроизводимого релиза — его digest. Digest не обновится сам, поэтому заведите регулярную проверку обновлений и процесс пересборки. Без этого pinning просто закрепит старый образ с известными уязвимостями.

## Оставьте наружу только reverse proxy

В Compose короткая запись `ports: ["8080:8080"]` обычно публикует порт на всех интерфейсах хоста. Если на VPS уже работает Nginx, привяжите внутренний порт приложения к loopback:

```yaml
ports:
  - "127.0.0.1:8080:8080"
```

Тогда внешний клиент не подключится напрямую к приложению, а Nginx на хосте сможет отправлять ему запросы. В Docker Engine младше 28.0.0 опубликованные на `127.0.0.1` порты могли быть доступны другим хостам из того же L2-сегмента; обновите Engine и проверьте сетевую доступность. Если reverse proxy сам работает в Compose, указывайте `ports` только у него; приложение и база общаются через сети Docker. В Compose можно явно задать `host_ip`; если его опустить, порт обычно привязывается ко всем интерфейсам. Подробности — в [описании публикации портов Docker](https://docs.docker.com/engine/network/port-publishing/) и [спецификации `ports` в Compose](https://docs.docker.com/reference/compose-file/services/).

Пример разделения сетей:

Это каркас топологии, а не готовый compose-файл: подставьте проверенные образы приложения и базы, настройки окружения, healthcheck и пути данных своего проекта. Образы можно задавать переменными в `.env.production` или через окружение деплоя; фиксируйте проверенный tag либо digest и храните сам файл конфигурации без секретов.

```yaml
services:
  proxy:
    image: ${PROXY_IMAGE:?set_proxy_image}
    ports:
      - "80:80"
      - "443:443"
    networks: [web]
    logging:
      driver: local
      options:
        max-size: "10m"
        max-file: "5"

  app:
    image: ${APP_IMAGE:?set_app_image}
    networks: [web, data]
    # Порт приложения не публикуется на хосте.

  db:
    image: ${DB_IMAGE:?set_db_image}
    networks: [data]
    volumes:
      # Этот путь подходит для официального образа PostgreSQL 17 и ниже.
      - db_data:/var/lib/postgresql/data
    # Порт базы не публикуется на хосте.

networks:
  web: {}
  data:
    internal: true

volumes:
  db_data: {}
```

В этой схеме proxy и приложение находятся в сети `web`, а база — только в `data`. Приложение может подключиться к базе по имени сервиса `db`. `internal: true` закрывает внешний маршрут для сети `data`, поэтому база не имеет собственного выхода наружу. Приложение подключено также к `web`, значит, по умолчанию у него остаётся исходящий доступ через эту сеть. Если приложению нельзя обращаться к произвольным внешним адресам, настройте фильтрацию исходящего трафика на хосте или выделенный egress-прокси. [Документация Compose о сетях](https://docs.docker.com/reference/compose-file/networks/).

Путь тома в примере зависит от версии официального образа PostgreSQL: в PostgreSQL 18 и новее каталог данных изменён, а volume нужно монтировать в `/var/lib/postgresql`. Перед выбором `DB_IMAGE` сверьте `PGDATA` и путь тома с документацией конкретного тега; при смене major-версии PostgreSQL планируйте миграцию базы отдельно, а не просто меняйте tag образа. [Документация официального образа PostgreSQL](https://github.com/docker-library/docs/blob/master/postgres/README.md#pgdata).

Если reverse proxy тоже работает в Compose, он обращается к приложению по имени сервиса и внутреннему порту. Например, в `server`-блоке Nginx:

```nginx
location / {
    proxy_pass http://app:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

Этот вариант предполагает, что клиент подключается прямо к Nginx. Если перед ним стоит CDN или внешний балансировщик, настройте доверие только к его адресам и корректное определение исходного IP: не принимайте переданный клиентом `X-Forwarded-For` как достоверный. TLS-сертификаты выпускайте и продлевайте автоматизированно; proxy достаточно смонтировать каталог сертификатов только для чтения, а права на выпуск/обновление оставьте отдельному процессу.

Сетевой сегмент ограничивает соединения между контейнерами, которые не включены в одну сеть. Он не заменяет проверку приложения и не изолирует враждебные контейнеры на уровне отдельного ядра.

## Запускайте приложение с минимальными правами

В Dockerfile задайте непривилегированного пользователя и права на нужные каталоги. При необходимости Compose может явно указать UID/GID:

```yaml
services:
  app:
    user: "10001:10001"
    read_only: true
    tmpfs:
      - /tmp:rw,noexec,nosuid,size=64m
    cap_drop:
      - ALL
    security_opt:
      - no-new-privileges:true
    volumes:
      - uploads:/srv/app/uploads
```

Это пример, а не набор флагов для бездумного копирования. Убедитесь, что указанный пользователь подходит образу, а все необходимые для работы каталоги смонтированы отдельно. Для именованного тома `uploads` добавьте его в корневую секцию `volumes` Compose-файла вместе с `db_data`, например `uploads: {}`. `read_only` может сломать приложение, если оно пишет кеш, сессии или временные файлы в корень контейнера. Начните с реально нужных путей и добавляйте права по одному, проверяя запуск и обработку запросов. Не используйте `privileged`, `network_mode: host`, host PID namespace или монтирование `/` и `/etc` без доказанной необходимости.

Задайте лимиты CPU, памяти и числа процессов, если их поддерживает ваша версия Compose и выбранная платформа. Они не предотвращают все сбои, но ограничивают влияние зациклившегося запроса или fork bomb. Проверяйте, что ограничения действительно применились, а не остались проигнорированными настройками.

## Отделите секреты от конфигурации

`.env.production` используйте для несекретных параметров: имени образа, домена, имени базы или режима логирования. Не храните там открытые пароли, если приложение затем передаёт их в окружение контейнера.

Docker Compose может смонтировать секрет файлом в `/run/secrets/<имя>` и дать доступ только тем сервисам, которым он нужен ([документация Compose](https://docs.docker.com/compose/how-tos/use-secrets/)):

```yaml
services:
  app:
    secrets:
      - app_db_password
    environment:
      DB_PASSWORD_FILE: /run/secrets/app_db_password

secrets:
  app_db_password:
    file: ./secrets/app_db_password.txt
```

`DB_PASSWORD_FILE` — соглашение конкретного приложения, а не специальная функция Compose. Приложение должно уметь читать пароль из файла; иначе настройте для него поддерживаемый способ передачи секрета.

В обычном локальном Compose секрет из `file:` — это bind mount файла с хоста. Compose не превращает такой файл в зашифрованное хранилище. Не добавляйте `secrets/` в Git, ограничьте права на исходные файлы на VPS и проверьте, что владелец и режим файла позволяют прочитать его UID процесса приложения, но не посторонним пользователям. Шифруйте резервные копии, куда секреты попадают. Для Swarm и внешних хранилищ секретов применяются другие модели защиты.

Для базы создайте отдельную учётную запись приложения с правами только на его базу и схему. Не подключайте веб-приложение как `postgres`, `root` или другого администратора. Административный пароль базы должен быть отдельным секретом, доступным только самой базе и процессу bootstrap/обслуживания.

## Храните данные и готовьте восстановление

Контейнер можно удалить и пересоздать; база, загрузки пользователей и другие постоянные данные должны жить в именованных томах или специально подготовленных каталогах хоста. Не записывайте состояние только в writable layer контейнера.

Резервные копии храните вне VPS и вне тех же Docker-томов, где лежат рабочие данные. Для базы используйте штатный механизм dump/backup либо согласованный snapshot, шифруйте копии и регулярно проверяйте восстановление на отдельном окружении. Наличие файла с названием `backup` ещё не доказывает, что из него можно восстановиться.

Не используйте `docker compose down -v` как обычную команду деплоя: ключ `-v` удаляет объявленные Compose тома и может удалить базу вместе с сайтом. Перед удалением тома проверяйте его имя и наличие проверенной резервной копии.

## Обновляйте и проверяйте развёртывание

Новая версия — это изменение образа, а не ручная правка работающего контейнера. Минимальный цикл выглядит так:

1. Собрать образ в CI, выполнить тесты и проверить образ на известные уязвимости.
2. Зафиксировать версию/digest образа в конфигурации релиза.
3. Сделать и проверить резервную копию перед миграциями схемы.
4. Применить конфигурацию и запустить Compose.
5. Проверить статус, логи, healthcheck и сайт извне.
6. Если новый релиз неисправен — вернуть предыдущий образ и применить совместимый план отката базы.

Пример базовых команд из каталога проекта:

```bash
sudo docker compose --env-file .env.production config
sudo docker compose --env-file .env.production pull
sudo docker compose --env-file .env.production up -d
sudo docker compose --env-file .env.production ps
sudo docker compose --env-file .env.production logs --tail=100
```

Не добавляйте секреты в `.env.production`, если вывод `docker compose config` будет сохранён в логе CI или тикете. Для каждого сервиса настройте healthcheck, который проверяет полезное для пользователя поведение. Restart policy возвращает процесс после завершения, но не чинит приложение, которое продолжает работать и отдаёт ошибки.

Ограничьте рост логов настройками драйвера логирования или централизованным сбором. В примере Compose используется драйвер `local` с ограничением размера и числа файлов; задайте аналогичные параметры и остальным сервисам. Следите за местом на диске, сроком TLS-сертификата, свободной памятью и успешностью последнего восстановления резервной копии.

## Проверочный чек-лист

### VPS и Docker Engine

- [ ] VPS запущен из чистого поддерживаемого образа; обновления ОС устанавливаются регулярно.
- [ ] Есть отдельная административная учётная запись и проверенный SSH-ключ; вход root и парольный вход отключены только после проверки альтернативного доступа.
- [ ] Firewall провайдера и хоста открывают только необходимые порты; SSH ограничен по источникам, если это возможно.
- [ ] Docker Engine и Compose установлены из подходящего для дистрибутива источника; версии записаны в инструкции.
- [ ] Выходят обновления Docker Engine и Compose plugin; обновления безопасности устанавливаются по принятому окну обслуживания.
- [ ] К Docker API и `/var/run/docker.sock` имеют доступ только доверенные администраторы; API не открыт наружу.
- [ ] Пользователи группы `docker` считаются администраторами хоста.
- [ ] Проверено с внешней машины, какие порты реально доступны; одной проверки `ufw status` недостаточно.

### Образы и Compose

- [ ] У каждого образа понятный источник и фиксированная версия; `latest` не используется как процесс обновления.
- [ ] Договорённость об обновлении digest/версий есть; устаревшие образы пересобираются и повторно проверяются.
- [ ] `.dockerignore` исключает `.git`, `.env`, секреты, резервные копии и локальные артефакты.
- [ ] `.env.production` и каталог `secrets/` исключены из Git; опубликованы только безопасные шаблоны конфигурации.
- [ ] Приложение работает без root, если это поддерживает образ; UID/GID согласованы с правами томов.
- [ ] Контейнеру не нужны `privileged`, host network/PID, Docker socket или широкие host mounts.
- [ ] `read_only`, `cap_drop`, `no-new-privileges` и лимиты включены там, где их проверили на конкретном приложении.
- [ ] Снаружи доступны только необходимые порты reverse proxy; порт приложения и базы не опубликован.
- [ ] Сервисы разделены Compose-сетями; база подключена только к нужной внутренней сети.
- [ ] Секреты не попадают в Git, Dockerfile `ARG`/`ENV` или открытые CI-логи.
- [ ] Nginx/Traefik/Caddy завершает HTTPS, сертификаты продлеваются автоматически, панель proxy недоступна из интернета.

### Данные и эксплуатация

- [ ] Постоянные данные вынесены из контейнеров в названные тома или подготовленные каталоги.
- [ ] Резервная копия хранится вне VPS, зашифрована и проверена тестовым восстановлением.
- [ ] Перезапуск, healthcheck и уведомление об ошибках настроены отдельно.
- [ ] Логи ограничены по размеру/сроку; контролируются место на диске и заполнение томов.
- [ ] Перед обновлением выполняется backup; есть проверенный способ отката приложения и базы.
- [ ] `docker compose down -v` не входит в обычную процедуру обновления.
- [ ] После деплоя проверяются HTTP-ответ, свежие логи и реальный список открытых портов снаружи.
