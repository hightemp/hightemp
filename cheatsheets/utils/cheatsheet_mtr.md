# mtr — диагностика сетевого маршрута

`mtr` сочетает поиск маршрута из `traceroute` с повторными замерами задержки и ответов, как в `ping`. Его удобно запускать там, где наблюдается проблема, например с рабочего компьютера, на котором периодически зависает соединение с сервисом.

**Хоп (hop)** — один шаг маршрута, обычно промежуточный маршрутизатор. `mtr` отправляет серии проб с возрастающим TTL. TTL ограничивает число шагов пакета. Для IPv6 аналогичное поле называется *Hop Limit*. Когда лимит исчерпан, маршрутизатор может ответить служебным сообщением ICMP. `mtr` использует эти ответы, чтобы показать промежуточные узлы и время ответа до каждого из них.

## Установка

```bash
# Debian и Ubuntu, пакет для терминала
sudo apt install mtr-tiny

# Fedora
sudo dnf install mtr

mtr --version
```

Если запуск завершается ошибкой доступа к сокету, проверь установку пакета и права на запуск `mtr-packet`. Это помощник `mtr`, которому нужен доступ к сетевым сокетам для отправки и получения проб.

## Быстрый старт

В командах подставь свой домен или IP вместо `example.com`.

```bash
mtr -t example.com             # интерактивный режим в терминале, q для выхода
mtr -w -n -c 30 example.com     # текстовый отчёт, 30 циклов, только IP в строках
mtr -w -b -c 30 example.com     # широкий отчёт с именами и IP узлов
```

Один цикл включает пробы по маршруту. Для короткого отчёта удобно начать с 30 циклов с обычным интервалом около секунды. Если проблема редкая, увеличь число циклов и запиши время замера.

| Ключ | Что делает |
|---|---|
| `-r`, `--report` | Собирает статистику, печатает отчёт и завершается |
| `-w`, `--report-wide` | То же в широком формате с полными именами узлов |
| `-c 30`, `--report-cycles 30` | Ограничивает замер 30 циклами |
| `-i 2`, `--interval 2` | Задаёт интервал между пробами для каждого узла в секундах |
| `-n`, `--no-dns` | Показывает IP узлов без обратного поиска имён. Если конечная цель задана доменом, `mtr` всё равно сначала узнаёт его IP |
| `-b`, `--show-ips` | Показывает имя и IP рядом, удобно вместе с `-w` |
| `-4` / `-6` | Выбирает IPv4 или IPv6 для проб |
| `-T` / `-u` | Выбирает TCP или UDP. По умолчанию используются ICMP Echo-пробы |
| `-P 443`, `--port 443` | Задаёт порт назначения для TCP или UDP-проб |

## Как читать отчёт

| Поле | Что означает |
|---|---|
| `Loss%` | Доля проб, для которых `mtr` не получил ответ к моменту формирования отчёта |
| `Snt` | Сколько проб отправлено для этой строки |
| `Last` | RTT последнего полученного ответа в миллисекундах |
| `Avg` | Средний RTT среди полученных ответов |
| `Best`, `Wrst` | Минимальный и максимальный RTT |
| `StDev` | Стандартное отклонение RTT, то есть разброс времени ответов вокруг среднего |

**RTT (Round-Trip Time)** — время от отправки пробы до получения ответа. Для каждой строки оно включает путь от точки запуска до отвечающего узла и путь ответа назад. Разница между соседними `Avg` сама по себе не измеряет задержку отдельного канала.

### Потери видны на одном узле

Условный отчёт для цели `203.0.113.10`.

```text
Hop                 Loss%   Snt   Last   Avg   Best   Wrst  StDev
1. 192.0.2.1         0.0%    30    0.4   0.5    0.3    1.0    0.2
2. 198.51.100.5     80.0%    30    5.3   5.4    4.9    6.0    0.4
3. 203.0.113.1       0.0%    30   11.0  11.1   10.4   12.5    0.5
4. 203.0.113.10      0.0%    30   12.1  12.2   11.5   13.6    0.6
```

Хоп 2 ответил на 6 из 30 проб, а цель ответила на все 30. Такая картина типична для маршрутизатора, который ограничивает частоту собственных диагностических ответов. `???` в промежуточной строке означает, что ответ от этого хопа не получен. Следующие строки показывают, доходили ли пробы дальше. [Пояснение проекта mtr](https://github.com/traviscross/mtr)

### Потери или рост задержки видны до цели

Если в повторных замерах потери появляются с какого-то хопа и видны дальше, включая конечный адрес, это повод проверить весь участок и путь ответов. Например, одинаковые 10% на хопах 3, 4 и у цели читаются как три отдельных замера. Проценты между строками не складываются. Рост RTT, который сохраняется и у цели, также заслуживает проверки, особенно если он совпадает по времени с проблемой приложения.

Маршрут туда и обратно может отличаться. Кроме того, при балансировке разные пробы могут идти через разные маршрутизаторы. Для сравнения запускай `mtr` с одной точки, с одинаковым протоколом и на тот же IP. Если доступна вторая сторона, замер оттуда даёт независимый взгляд на обратное направление.

## Практические команды

### Сравнить ICMP с TCP на порту сервиса

```bash
mtr -4 -w -n -c 30 example.com
mtr -4 -w -n -c 30 -T -P 443 example.com
```

TCP-пробы стоит сравнивать с ICMP, когда проблема наблюдается у HTTPS-сервиса. `-T -P 443` использует TCP SYN-пробы к порту 443. Отказ TCP (`RST`) от закрытого порта тоже учитывается как ответ. Для проверки TLS и HTTP отдельно нужен запрос приложением, например `curl`. Промежуточные маршрутизаторы и при TCP-замере обычно отвечают служебными сообщениями ICMP.

### Сравнить IPv4 и IPv6

```bash
mtr -4 -w -n -c 30 example.com
mtr -6 -w -n -c 30 example.com
```

У разных семейств IP могут быть разные маршруты и точки входа в сервис. Замер по IPv6 требует рабочего IPv6-маршрута и IPv6-адреса у цели.

### Проверить маршрут при VPN или нескольких интерфейсах

```bash
ip route get 203.0.113.10
mtr -4 -w -n -c 30 -a 192.0.2.10 203.0.113.10
```

Подставь целевой IP и локальный исходный IP. `ip route get` показывает решение ядра о маршруте, в том числе выбранный интерфейс (`dev`) и исходный адрес (`src`). `-a` привязывает пробы `mtr` к заданному локальному адресу. Для сравнения замеров до и после подключения VPN записывай, с какого адреса и на какой IP шли пробы.

### Проверить доступность и скорость VPN

**1. Проверь внешний маршрут до VPN-сервера.** На клиенте с отключённым VPN выполни замер из сети, где возникает проблема. Вторую команду используй, если VPN работает по TCP.

```bash
mtr_vpn_ip=203.0.113.10  # публичный IP VPN-сервера
mtr_vpn_port=443         # фактический порт TCP-VPN

mtr -n -w -c 30 "$mtr_vpn_ip"
mtr -n -w -c 30 -T -P "$mtr_vpn_port" "$mtr_vpn_ip"
```

Сравни потери у конечного адреса. TCP-отчёт показывает ответы на пробы, включая `RST` от закрытого порта. Установление VPN проверяй в самом клиенте.

**2. Проверь туннель.** Для WireGuard отправь трафик до внутреннего адреса сервера и посмотри состояние интерфейса.

```bash
ping -c 3 10.66.66.1  # внутренний IP VPN-сервера
sudo wg show wg0     # имя интерфейса WireGuard
```

Свежий `latest handshake` подтверждает обмен ключами. Ответ на `ping` подтверждает, что тестовый трафик прошёл через туннель. Если внутренний адрес фильтрует ICMP, проверь доступный через VPN сервис. Счётчики `received` и `sent` помогают сравнить объём обмена до и после проверки. WireGuard может молчать на обычную UDP-пробу `mtr`. Если подключение не устанавливается, повтори проверку с того же клиента через другую сеть, например через мобильную точку доступа. [Протокол WireGuard](https://www.wireguard.com/protocol/) · [Руководство wg(8)](https://man7.org/linux/man-pages/man8/wg.8%40%40wireguard-tools.html)

**3. Замерь скорость.** `mtr` показывает задержки и потери ответов. Для измерения пропускной способности используй один и тот же контрольный узел `iperf3`, доступный напрямую и через VPN. Возьми отдельный адрес, поскольку публичный адрес VPN-сервера обычно маршрутизируется в обход туннеля даже при включённом VPN.

```bash
mtr_speed_test_ip=198.51.100.20  # IP контрольного сервера с iperf3
ip route get "$mtr_speed_test_ip"

iperf3 -c "$mtr_speed_test_ip" -t 30 -O 3     # от клиента к контрольному узлу
iperf3 -c "$mtr_speed_test_ip" -R -t 30 -O 3  # от узла к клиенту
```

Повтори обе команды с VPN и без VPN, каждый раз сверяя маршрут. Сравни `receiver` для каждого направления в нескольких замерах. Чтобы измерить участок от клиента до своего VPN-сервера, можно запустить на нём `iperf3 -s -B 10.66.66.1` и указать этот внутренний IP клиенту при включённом туннеле. [Руководство iperf3](https://software.es.net/iperf/invoking.html)

Повторяемый потолок скорости только через одну сеть — повод проверить возможное ограничение. Сравни тот же VPN через другого провайдера и проверь загрузку CPU на клиенте и сервере. Скорость через контрольный узел также зависит от маршрута от VPN-сервера до этого узла.

### Сохранить результаты для разбора

```bash
mtr_target=example.com
mtr_stamp=$(date +%Y%m%d-%H%M%S)

mtr -w -n -c 30 "$mtr_target" | tee "mtr-icmp-$mtr_stamp.txt"
mtr -w -n -T -P 443 -c 30 "$mtr_target" | tee "mtr-tcp-443-$mtr_stamp.txt"

mtr -n -j -c 30 "$mtr_target" > "mtr-$mtr_stamp.json"
mtr -n -C -c 30 "$mtr_target" > "mtr-$mtr_stamp.csv"
```

`-j` даёт JSON, `-C` — CSV. Каждая команда проводит самостоятельный замер. Доступность форматов можно проверить через `mtr --help`. Вместе с отчётом зафиксируй дату и часовой пояс, место запуска, целевой IP, протокол проб и порт.
