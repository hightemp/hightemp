# tcpdump — захват и анализ сетевых пакетов

`tcpdump` показывает пакеты, видимые на выбранном сетевом интерфейсе. С его помощью можно проверить, ушёл ли DNS-запрос, пришёл ли ответ на TCP-подключение и на каком интерфейсе появляется трафик VPN. Утилита также читает сохранённые захваты **PCAP** — файлы с отметками времени и байтами пакетов.

## Установка

```bash
# Debian и Ubuntu
sudo apt install tcpdump

# Fedora
sudo dnf install tcpdump

tcpdump --version
```

Для захвата на интерфейсе нужны соответствующие права. Сохранённый файл обычно можно прочитать обычным пользователем, если у него есть доступ к файлу.

## Первые команды

```bash
sudo tcpdump -D                        # список интерфейсов для захвата
sudo tcpdump -i any -nn -c 20           # вывести 20 пакетов
sudo tcpdump -i eth0 -nn -tttt -c 30 'host 203.0.113.10 and tcp port 443'
```

Подставь имя своего интерфейса и адрес проверяемого узла. В Linux `any` слушает несколько сетевых интерфейсов. Для сравнения внешнего и внутреннего трафика VPN указывай конкретный интерфейс. Захват можно остановить через `Ctrl+C`. При `-c` команда завершится после указанного числа пакетов, **прошедших фильтр**.

| Ключ | Что делает |
|---|---|
| `-i eth0` | Захватывает пакеты на интерфейсе `eth0` |
| `-nn` | Показывает IP и порты числами, без поиска имён |
| `-t` / `-tttt` | Скрывает время или показывает дату и время для каждого пакета |
| `-v`, `-vv` | Добавляет детали при разборе пакета |
| `-c 20` | Останавливает захват или чтение после 20 подходящих пакетов |
| `-s 128` | Сохраняет до 128 первых байт каждого пакета |
| `-s 0` | Выбирает стандартную длину захвата. В актуальном `tcpdump` это 262 144 байта |
| `-w capture.pcap` | Записывает бинарный захват в файл. `-w -` отправляет его в стандартный вывод |
| `-r capture.pcap` | Читает захват из файла |
| `-X` / `-XX` | Показывает байты пакета в шестнадцатеричном виде и ASCII. `-XX` включает и заголовок канального уровня |

**Snaplen** — предел числа байт, сохраняемых для одного пакета. Слишком маленькое значение может обрезать часть заголовков или данных. Вывод `[|протокол]`, например `[|tcp]`, указывает, где для декодирования не хватило сохранённых байт.

## Фильтры захвата

`tcpdump` компилирует выражения в фильтр BPF (*Berkeley Packet Filter*). Фильтр выбирает пакеты по полям заголовков. В командах заключай выражение в одинарные кавычки, чтобы Bash передал его целиком.

| Фильтр | Какие пакеты выбирает |
|---|---|
| `host 203.0.113.10` | От этого узла или к нему |
| `src host 192.0.2.10` | Только от указанного источника |
| `dst net 192.0.2.0/24` | К адресам указанной подсети |
| `tcp port 443` | TCP с портом 443 в источнике или назначении |
| `tcp dst port 443` | TCP, направленный на порт 443 |
| `udp port 53` | UDP с портом 53 в любом направлении |
| `portrange 8000-8010` | Пакеты с портом в указанном диапазоне |
| `ip6 and tcp port 443` | IPv6-пакеты TCP с портом 443 |
| `icmp or icmp6` | Служебные сообщения ICMP для IPv4 и IPv6 |

`and` требует выполнения обоих условий, `or` — хотя бы одного, `not` исключает совпадения. У `and` и `or` одинаковый приоритет, поэтому при сочетании используй скобки. Следующий фильтр выбирает TCP и UDP к порту 443 на одном адресе.

```bash
sudo tcpdump -i eth0 -nn -c 30 '(tcp or udp) and dst port 443 and host 203.0.113.10'
```

## Практические примеры

### Проверить TCP-подключение к сервису

```bash
sudo tcpdump -i any -nn -tttt -c 30 'host 203.0.113.10 and tcp port 443'
```

При открытии TCP-соединения ищи такую последовательность. Условный пример, в котором клиент использует временный порт `51000`.

```text
12:00:00.100000 IP 192.0.2.10.51000 > 203.0.113.10.443: Flags [S], length 0
12:00:00.120000 IP 203.0.113.10.443 > 192.0.2.10.51000: Flags [S.], length 0
12:00:00.120100 IP 192.0.2.10.51000 > 203.0.113.10.443: Flags [.], length 0
```

`[S]` — SYN, запрос на установку соединения. `[S.]` — SYN+ACK, ответ на запрос. Точка обозначает ACK, подтверждение. `[R]` и `[R.]` обозначают сброс TCP-соединения. Если видны повторные SYN без ответа, проверь обратное направление и точку захвата. Для HTTPS этот вывод показывает состояние TCP, а результат TLS и код ответа HTTP нужно проверять на уровне приложения.

Можно сузить захват до начальных SYN или сбросов. `tcp[tcpflags]` обращается к полю флагов TCP, а `&` выбирает нужные биты.

```bash
# Начальный SYN с установленным SYN и сброшенным ACK
sudo tcpdump -i any -nn -c 20 'ip and tcp port 443 and tcp[tcpflags] & (tcp-syn|tcp-ack) = tcp-syn'

# Сбросы соединений на порту 443
sudo tcpdump -i any -nn -c 20 'ip and tcp port 443 and tcp[tcpflags] & tcp-rst != 0'
```

В этих примерах фильтр по байтам заголовка явно ограничен IPv4. Для захвата IPv6-соединения используй `ip6 and tcp port 443` и смотри флаги в выводе. [Руководство pcap-filter(7)](https://manpages.debian.org/trixie/libpcap0.8t64/pcap-filter.7.en.html)

### Проверить DNS

```bash
sudo tcpdump -i any -nn -vv -c 20 '(udp or tcp) and port 53'
```

Выполни обычный DNS-запрос и найди в выводе имя, тип записи и ответ с тем же идентификатором транзакции. `NXDomain` означает, что DNS-сервер ответил и сообщил об отсутствии такого имени. Системный резолвер может ответить из кэша, а DNS поверх HTTPS или TLS идёт по другому подключению. При локальном резолвере проверяй и интерфейс `lo`.

В этом сокращённом примере запрос записи `A` и ответ `NXDomain` имеют идентификатор `1234`.

```text
12:00:01.000000 IP 192.0.2.10.44511 > 198.51.100.53.53: 1234+ A? example.test. (30)
12:00:01.020000 IP 198.51.100.53.53 > 192.0.2.10.44511: 1234 NXDomain 0/0/0 (30)
```

### Сравнить внешний и внутренний трафик WireGuard

```bash
# Внешние UDP-пакеты на интерфейсе, через который доступен VPN-сервер
sudo tcpdump -i eth0 -nn -tttt -c 30 'host 203.0.113.10 and udp port 51820'

# Пакеты к внутреннему адресу при тестовом ping через туннель
sudo tcpdump -i wg0 -nn -tttt -c 20 'icmp and host 10.66.66.1'
```

Подставь внешний интерфейс, публичный IP и фактический порт WireGuard. Для второй команды используй своё имя туннельного интерфейса и внутренний IP. Первый захват показывает внешний обмен UDP, второй помогает увидеть, проходит ли тестовый трафик внутри туннеля. Проверку маршрута и скорости смотри в [шпаргалке по mtr](cheatsheet_mtr.md#проверить-доступность-и-скорость-vpn).

## Записать и открыть PCAP

```bash
# Сохрани до 200 подходящих пакетов в файл своего пользователя
sudo tcpdump -i eth0 -s 0 -U -c 200 -w - 'host 203.0.113.10 and tcp port 443' > capture.pcap

# Текстовое чтение захвата
tcpdump -nn -tttt -r capture.pcap

# Отфильтровать уже записанные пакеты и ограничить вывод
tcpdump -nn -c 10 -r capture.pcap 'tcp dst port 443'

# Посмотреть байты нескольких сохранённых пакетов
tcpdump -nn -X -c 3 -r capture.pcap
```

При `-w -` оболочка создаёт файл через `>`, а `tcpdump` пишет туда бинарные данные. `-U` сбрасывает выходной буфер после каждого пакета. Оставляй сообщения об ошибках и статистику в стандартном потоке ошибок, чтобы они не попали в PCAP. Захват с полной длиной пакета может содержать данные приложения.

Для длительного наблюдения можно ограничить объём записи кольцом файлов. Каталог должен существовать и быть доступен на запись тому пользователю, от которого `tcpdump` записывает файлы.

```bash
sudo tcpdump -i eth0 -C 20 -W 4 -w /var/tmp/pcap/traffic.pcap 'host 203.0.113.10'
```

`-C 20` переключает запись на следующий файл примерно при 20 млн байт. `-W 4` оставляет четыре файла и затем перезаписывает старые по кругу.

## Как читать диагностику захвата

- **`packets dropped by kernel`** — пакеты, которые не поместились в буфер локального захвата. Сузь фильтр, попробуй запись в файл или увеличь буфер через `-B 4096` (КиБ). [Руководство tcpdump(8)](https://manpages.debian.org/trixie/tcpdump/tcpdump.8.en.html)
- **`bad checksum` у исходящего TCP или UDP** может быть следствием *checksum offload*. Сетевая карта рассчитывает контрольную сумму уже после точки, где ядро передало копию пакета в захват. Для чтения такого вывода можно отключить проверку контрольных сумм ключом `-K`. [Документация ядра Linux](https://docs.kernel.org/networking/checksum-offloads.html)
